A checkerboard that knows where it is

The fine pose already works on a checkerboard. Here is how to give it the absolute one — by inverting a single square in each 3×3 block — and the measurements showing the code does not touch the fine phase it rides on.

Implemented on branch worktree-checkerboard-pattern. Every number below comes from vernier checkerboard-figures; every figure is that command's output.

The idea, in two pictures

Same board, same pose. On the left the plain carrier; on the right the same carrier with an order-8 position code written into it. Every defect you can see is one square painted against its checkerboard parity.

A checkerboard is a megarena at full fill

This is the observation that makes the whole thing cheap. A checkerboard of square side a is the megarena's dot lattice rotated 45° and filled in completely — so the existing two-peak spectral search, the phase planes, the thumbnail, the LFSR all transpose without modification.

Write s(x) = sign(cos(π(x/a − ½))) for the square wave of one axis. The board is s(x)·s(y), and the product of two square waves keeps only odd×odd harmonics — so nothing at all lands on the frequency axes, and the lowest terms are a pair of diagonal carriers:

(8/π²) · [ cos φ₁ + cos φ₂ ]   with   φ₁ = π((x+y)/a − 1)   φ₂ = π(x−y)/a

How a bit is written

Squares group into 3×3 supercells. Two squares per supercell carry code: the one at (1,0) holds the x-code bit of its supercell column, the one at (0,1) the y-code bit of its row. A site whose bit is 0 is painted against its parity. Everything else is left alone.

Reading a bit is then one question: does this square's colour disagree with (i+j) mod 2?

No reference marks are needed to answer it. The eight neighbours of every coding site are guaranteed-correct squares of both colours, which is a free local black and white reference — the megarena has to spend dedicated reference dots on the same job.

x-code site y-code site filled centre = inverted, i.e. a 0 bit

Three properties, and what they measure

These are not steps in a process; they are the three things the design has to be true for it to be worth building, each with the number that came back.

Balanced

0.5000 white

Measured over a whole code period. Because coding sites alternate parity, half the inversions go white→black and half the other way, so the fill does not drift with the code. A megarena cannot have this: a removed dot is always a loss of white.

Phase-neutral

4.0 mrad rms

A square centre is an extremum of both carriers, so inverting it is a purely real perturbation in the carrier basis — it shrinks the peak, it never rotates it. At a 10 µm square that residual is about 9 nm of position.

Cheap

77.7% carrier kept

Roughly one square in nine flips, each costing twice its own contribution. And it is spent from a much larger budget: the uncoded checkerboard puts 0.40 of full scale into each carrier against the megarena dot's 0.25.

Only the average over a whole period is a fair number. A window that happens to sit on the sequence's run of ones reports 87 %, which is true and misleading.

Reading it back

Five steps, in order, from phase planes to an absolute square index. All of it lives in vernier-pose/src/checkerboard.rs.

  1. Sample. With s = φ₁/π and d = φ₂/π, the continuous square coordinates are î = (s+d)/2 and ĵ = (s−d)/2. Pixels close to a lattice point on both axes are pooled into that square's mean intensity; edge pixels, which carry the transition, are dropped.
  2. Binarize. The board is 50/50 by construction, so the mean of all square samples already sits between the two populations. One k-means step centres it. The balance property is what makes a global threshold viable at all.
  3. Build the defect map. Mark every square whose colour disagrees with (i+j) mod 2. The right parity hypothesis defects about 1 square in 9; the wrong one about 8 in 9 — so the black/white ambiguity resolves itself, with no search.
  4. Place the supercell grid. The frame offset is known only modulo 3, so all nine offsets are tried × the four rotations. Each choice says exactly which squares carry which code.
  5. Localize. One bit per supercell per axis; order bits fix the position in the LFSR sequence, and every further bit checks it.

Against ground truth — render at a known pose, decode, compare to the square the image centre actually sits on — this recovers the right square out of 765 across translations spanning the whole board and through rotation, and the continuous position to better than 0.25 px.

The trap: every window localizes

A maximal LFSR of order n contains every non-zero n-bit word exactly once. So a window always decodes — including one read in the wrong orientation, which decodes confidently to the wrong place. No single window can ever be used to choose between hypotheses. The decoder over-reads instead: it locates on order bits and requires every remaining bit to agree. A typical field leaves 13 spare bits per axis, so a wrong hypothesis survives with probability 2⁻¹³.

Worth stating plainly, because the opposite is the natural assumption: a wrong orientation cannot be rejected on the grounds that its window "isn't in the sequence". It always is.

The subtler trap: the board is mirror-symmetric

Both axes carry the same LFSR. Transpose i and j and you swap the two coding sites and their two codes — and get the pattern back exactly. So a mirrored reading of the frame decodes just as convincingly, into a position reflected about the diagonal. Check bits cannot separate them — it surfaces as a decode that is off by one square along the anti-diagonal, with every check bit agreeing.

Nothing in the image is mirrored — the mirroring comes from the peak search, which may return the two carrier directions in either order. That is recoverable from the carriers themselves: ∇φ₁ and ∇φ₂ have a negative cross product, and rotating the board does not change that sign. A positive one means the directions came back swapped, and negating φ₂ restores the convention. After that only four rotations remain, and their coding-site offsets are all different.

And one more: the code period is odd

The range is 3·(2ⁿ−1) squares — 765 at order 8 — which is always odd, while the checkerboard parity has period 2. Shifting by one whole code period lands on the same code with the colours swapped, so the board only truly repeats after two code periods. Any check of the form "the frame offset must preserve parity" is therefore invalid, because the offset is only known modulo an odd number. The spare factor of two in range is real and is left on the table.

Sizing

Three squares per bit per axis. The field of view has to hold order bits plus a few spares in both directions.

One thing to watch when comparing with an existing megarena: the carrier period is a√2, not a. At the same number of camera pixels per fringe the checkerboard square is 1/√2 of a megarena period, so range shrinks by √2 — which one extra bit of code depth more than buys back.

  • vernier-patterns/src/checkerboard.rs — the pattern: layout, phases, renderer. Eleven tests, including the phase-neutrality property and the 50/50 balance over a whole code period.
  • vernier-pose/src/checkerboard.rs — the decoder, and a CoarseDecoder impl so it plugs into the existing absolute-pose assembly.
  • vernier-pose/tests/checkerboard_absolute.rs — the ground-truth round trip, across translation, rotation, sub-square position, and a too-small field that must fail rather than guess.
  • vernier-cli/src/commands/ — render_checkerboard.rs and checkerboard_figures.rs.
  • Reused unchanged: lfsr.rs, the spectral pipeline, the phase planes. No change to any existing pattern.

Not done, and deliberately not done

Open

  • Orientation convention. θ comes out as the fine plane angle less the winning rotation's quarter-turn. Tests only exercise |θ| < 0.8 rad; the quadrant convention wants checking against the C++ computeAbsolutePose before anyone trusts it near the diagonals.
  • Real images. Binarization is a global threshold. It works because the board is balanced, but an illumination gradient would want a local one. Nothing here has met a camera yet.
  • Noise tolerance. The decoder allows one wrong bit per axis. That number is a guess, not a measurement.
  • No C++ port. Rust only, so far.

Considered and not taken

A dotted board — leave the checkerboard untouched and put a small opposite-colour dot at the centre of coding squares. The saddle points survive, so findChessboardCorners and ChArUco-style detection keep working on the same target. Worth doing if the board should double as a calibration target; it costs a little balance and a little carrier.

A 2D perfect map (De Bruijn torus) instead of two separable sequences — a much smaller field of view, a square window instead of a full row and column, at the price of a hash-table decode and no reuse of the existing LFSR machinery. Only worth it if the field is tight.

And the tempting one that breaks everything: encoding by nudging every third grid line by ±δ. It keeps every square and every corner intact — and it is phase modulation by definition, so it biases the very quantity we measure. It trades the thing that already works for the thing we want.
